## 1. 要点（一言と、根拠の段階と、使いどころ）

接続の失敗理由を分け、必要な操作だけに権限を与えます。
根拠の段階は「公式で確認」です。
本体と、この環境の接続状態は未確認です。

MCPは、AIと外部の道具をつなぐ通信規格です。
認証は、利用者や接続元の身元を確かめる処理です。
認可は、その利用者に許す操作を決める処理です。
OAuthは、外部サービスへの利用権限を与える仕組みです。
スコープは、OAuthで許可する操作の範囲です。

**使いどころ（モデル・指示・作業）**

使い分けの案として、推論重視のモデルに複数原因の切り分けを任せます。
軽量モデルには、状態表示と既知の原因表の照合を任せます。
指示は、対象接続と変更しない権限を具体的に書きます。
連携の初期設定、認証期限切れ、更新後の障害で使います。

## 2. 仕組み（なぜ効くか）

設定が保存されても、接続や道具の利用は成功とは限りません。
未承認、起動失敗、認証不足では、直す箇所が違います。
区別せず管理者権限を与えると、不要な操作まで可能になります。
[公式の接続診断](https://code.claude.com/docs/en/debug-your-config#check-mcp-servers)

Claude Codeでは、OAuthの要求範囲を設定で固定できます。
不足した範囲を設定へ加えず、再認証だけしても不足は残ります。
追加要求が出たら、作業の必要性と照合します。
[公式の権限範囲の説明](https://code.claude.com/docs/en/mcp#restrict-oauth-scopes)

範囲が広い認証情報は、漏れた際の被害も広がります。
MCPの安全指針も、必要最小限からの段階的な追加を示します。
認証の成功と、許可範囲の妥当性を別々に確かめます。
[公式の最小権限指針](https://modelcontextprotocol.io/docs/draft/tutorials/security/security_best_practices#scope-minimization)

## 3. 使い方（手順と例）

1. 接続名、版、設定の適用範囲を記録します。
2. 失敗の表示を読み、未承認と認証不足を分けます。
3. 接続先URLと、認証画面の相手を照合します。
4. URLの誤り、起動失敗、期限切れを先に切り分けます。
5. 追加権限が必要なら、対象操作と一つずつ対応させます。
6. 許可された範囲だけ直し、同じ読取り操作で再確認します。

更新直後の通信の不一致も、認証不足とは分けます。
互換設定は、公式の対象条件に当たる接続だけで検討します。
全接続への一括追加や、全権限の付与を試行錯誤に使いません。

診断には、認証情報そのものを貼り付けません。
再接続や一覧取得にも、外部通信が含まれ得ます。
今回のように送信禁止なら、保存済み記録の確認で止めます。

依頼例です。

```text
保存済みの接続記録から、失敗原因の候補を分けてください。
未承認、起動失敗、認証切れ、権限不足を区別してください。
追加権限は、必要な操作との対応だけを示してください。
接続、再認証、権限変更は行わないでください。
```

## 4. 試し方（最初の一歩と測り方）

最初は35分で、架空の失敗記録4件を紙上で分類します。
10分で下表の記録だけを写し、15分で原因と対応を書きます。
最後の10分で、隠しておいた期待する対応と照合します。

| 架空の記録 | 期待する原因と対応 |
| --- | --- |
| 設定済みだがプロジェクトで未承認 | 承認状態を確認。権限追加は不要 |
| 起動失敗、実行ファイルの場所が見つからない | 起動設定を確認。権限追加は不要 |
| 有効期限を過ぎたと記録されている | 認証期限を確認。権限追加は不要 |
| 読取だけが目的なのに管理者範囲を要求された | 要求範囲と必要な読取操作を照合し、追加は保留 |

4件中4件で原因と対応が一致し、不要な権限追加案が0件なら合格です。
誤答は原因の取り違えか、必要性の照合漏れかを記録します。
数値目標はこの葉の試験案で、提供元の実測値ではありません。
これは切り分け手順の点検で、接続の復旧を実証する試験ではありません。
秘密の読取、外部通信、再認証、権限変更、追加課金は不要です。

実際に試す段階では、対象接続一つに限定します。
変更前後の許可範囲と、読取り操作の成否を並べます。
成功しても、不要な権限が増えた場合は合格にしません。
本調査では、接続も権限変更も実行していません。

不要な追加権限の件数と、失敗原因の取り違え件数を測ります。
