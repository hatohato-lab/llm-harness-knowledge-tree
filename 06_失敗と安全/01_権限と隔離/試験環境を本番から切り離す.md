## 1. 要点（一言と、根拠の段階と、使いどころ）

試すための失敗が、本番のデータや操作に届かないようにします。

- 根拠の段階：公式で確認
- 使いどころ：自動修正、自己改善、未知の道具の試行。
- 賢いモデルには、境界の設計と漏れの点検を任せます。
- 軽いモデルには、具体的な試験手順を渡します。
- 効果の大小と、私の環境での動作は未確認です。

本番は、実際の利用者や業務へ影響する環境です。
試験環境は、失敗を調べるために分けた環境です。
資格情報は、サービスへの接続を許す鍵などの情報です。
仮想マシンは、独立した基本ソフトを持つ実行環境です。

## 2. 仕組み（なぜ効くか）

安全に試すには、保存場所を分けるだけでは足りません。
同じ鍵や接続先を使えば、本番への操作は残ります。
入力、出力、鍵、通信先を一緒に切り分けます。
これは公式の隔離範囲を、試験設計へ当てはめた案です。
[隔離環境の比較](https://code.claude.com/docs/en/sandbox-environments)

別の環境でも、本番を読書きできる設定なら影響が届きます。
クラウドで動くというだけでは、本番分離の保証になりません。
Claudeの公式は、環境ごとの隔離と通信制御を説明します。
自社で用意した環境では、運用者が境界を管理します。
[クラウドの隔離](https://code.claude.com/docs/en/claude-code-on-the-web#security-and-isolation)

自己改善の研究にも、実行環境を分けた例があります。
DGMは、自分のコードを変更して候補を試す研究です。
その研究では隔離、時間制限、変更の監視を併用しました。
本番業務で安全に自動改善できる実証とは区別します。
[DGM論文の安全性の議論](https://arxiv.org/html/2505.22954v3#S5)

## 3. 使い方（手順と例）

1. 試したい失敗と、影響させない対象を決めます。
2. 架空の入力と、専用の出力先を用意する案を作ります。
3. 本番の鍵や接続先を引き継ぐ設定がないか確かめます。
4. 自動公開や自動送信につながる処理も調べます。
5. 試験結果と、本番への反映判断を分けて残します。

以下は、資料更新の試験計画の例です。

```text
対象：架空の保守資料を5件
変更先：試行専用の複製
比較：元の資料と変更案の差分
成功：意図した誤りだけを修正
停止：本番の場所や接続を要求した時
報告：結果と未確認点を残す
```

公開や送信を伴う処理は、試験用の結果記録に置き換えます。
例えば、通知文を送らず、宛先名と文面の案を保存します。
これは本番の成否ではなく、判断内容を試す方法です。

外部サービスを使う隔離環境は、資料の転送を伴います。
今回の作業では、作成、転送、課金を行いません。
クラウド製品の並列上限も、推奨人数とは扱いません。

隔離内で動かない時に、勝手に別の外部環境へ移しません。
保存投稿には、動作不能から外部へ送信した体験談があります。
元の環境でできない事実を残し、停止条件として扱います。
この事例の再現と、現在の製品での動作は未確認です。

## 4. 試し方（最初の一歩と測り方）

最初は50分で、架空の入力を使う机上試験をします。
10分で下の5対象の境界を書き、各対象に正常例と違反例を1件ずつ作ります。
例えば架空の入力と実在の入力、試験用の鍵と本番用の鍵を対にします。
15分で旧手順、15分で新手順を同じ10件に適用します。
最後の10分で、先に決めた期待値と判定を照合します。

| 確認する対象 | 試験で許す範囲 |
| --- | --- |
| 入力 | 架空の例だけ |
| 書込み | 専用の結果だけ |
| 接続 | 試験用に決めた先だけ |
| 鍵 | 本番用は渡さない |
| 公開・送信 | 試験中は結果の記録へ置換 |

合格は正常例の正答5/5件、違反例の停止5/5件です。
本番の鍵・場所・接続先を使えるとした判断は0/10件にします。
判定不能は0件を目標にし、あれば不合格として境界を補います。
旧手順と新手順の正答数/10件、手戻り数、所要時間を並べます。
数値はこの葉の試験案であり、提供元の実測値ではありません。
実際の接続、送信、課金、設定変更を伴わない試験です。
紙上の合格は設計の確認で、実環境の分離や拒否動作の実証ではありません。
本番に近い条件をどこまで再現したかと、未確認点も記録します。
