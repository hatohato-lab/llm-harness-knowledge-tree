## 1. 要点（一言と、根拠の段階と、使いどころ）

応答を止めた後も、背景の作業と予定を一覧で確かめます。

- 根拠の段階：公式で確認。
- 担当と予定の停止方法を、公式文書で確認しました。
- 監視が止まった時の検知は、著者の公開資料で確認しました。
- 賢いモデルと軽いモデルの、どちらにも必要です。
- 指示は具体的にし、停止対象のIDと確認方法を示します。
- 並列調査、定期確認、夜間検査の管理に向きます。

背景実行は、会話の応答とは別に処理が動くことです。
担当IDは、動いている一つの担当を識別する値です。
監視役は、処理の状態や結果の時刻を確かめる処理です。

## 2. 仕組み（なぜ効くか）

応答、背景担当、定期予定は、別の状態を持ちます。
一つを止めても、残った処理が新しい操作を始め得ます。
停止対象を一覧にし、停止後の状態を読む必要があります。

Claude Codeでは、対象の担当を一覧から停止できます。
人が `x` で止めた担当は、AIの連絡では自動再開しません。
[公式の担当再開条件](https://code.claude.com/docs/en/sub-agents#resume-subagents)

`CronList` は、予定のIDと内容を一覧にする道具です。
`CronDelete` は、IDを指定して予定を取り消す道具です。
固定間隔の予定は、応答を止める `Esc` だけでは消えません。
[公式の予定管理](https://code.claude.com/docs/en/scheduled-tasks#manage-scheduled-tasks)

監視役が止まると、不具合の通知も途絶えます。
無通知を正常とせず、最後の確認時刻も別に見ます。
著者のMuraqibは、夜間検査の停止も検知する構成です。
[Muraqibの公開資料](https://github.com/holistis/muraqib)

## 3. 使い方（手順と例）

1. 担当、背景処理、定期予定の名前とIDを記録します。
2. 誰がどの方法で止めるか、開始前に決めます。
3. 停止時は、新しい起動元となる予定も対象にします。
4. 動いている子の担当や処理が残っていないか確かめます。
5. 停止状態と、停止後の新しい出力がないことを確認します。
6. 最後の確認時刻と、再開条件を記録します。

| 確かめる対象 | 確認する内容 |
|---|---|
| 今の応答 | 応答が終わったか |
| 背景の担当 | 対象IDが停止状態になったか |
| 定期予定 | 対象IDが一覧から外れたか |
| 監視役 | 最後の検査時刻が古すぎないか |
| 子の処理 | 親の終了後も残っていないか |

Claude Codeの `/tasks` は、背景の作業を確認する入口です。
一覧の対象を確かめてから、該当する担当を停止します。
自動で次の間隔を決める `/loop` は、別の停止規則です。
その待機中の `Esc` は、次の実行待ちを取り消します。
固定間隔の予定と混同しません。
[公式のループ停止](https://code.claude.com/docs/en/scheduled-tasks#stop-a-loop)

監視の試行では、正常、検査失敗、検査停止を分けます。
別の時計と記録から、結果の古さを判定する案にします。
検査全体の時間上限は、外側の上限より短くします。
報告のための時間を残す設計です。
[検査全体の時間制限](https://playwright.dev/docs/test-timeouts#global-timeout)

親が終わっても残る処理や、空き容量不足も監視候補です。
この追加監視は保存投稿の提案で、効果は未確認です。
既存の処理を勝手に止める命令としては使いません。

故障域は、一つの故障で一緒に止まり得る範囲です。
保存投稿には、容量不足で通知役も止まった体験談があります。
サービスが止まっても通知が届かず、発見が遅れたといいます。
これは体験談だけで、障害記録の直接確認は未実施です。

対策案では、監視先と同じ故障域だけに通知役を置きません。
別の基盤から、最後の確認時刻を読む構成を検討します。
同じ保存先だけに記録を残す場合も、同時停止を疑います。
別の監視役が止まる場合も含め、模擬記録で確かめる案です。
この分離策の効果は、本作業では未実証です。

## 4. 試し方（最初の一歩と測り方）

最初の一歩は、次の架空記録5件を紙に写すことです。
準備10分、判定20分、答え合わせ15分の計45分で試します。
各行は独立した場面です。実際の処理は起動しません。
ここで使う数値と合格値は、この葉の試験案です。
提供元が測った停止性能や推奨値ではありません。

| 架空の記録 | 残った担当 | 残った予定 | 停止後の新規処理 | 期待する判定 |
|---|---:|---:|---:|---|
| 親の応答だけ停止 | 1 | 1 | 1 | 停止未完了 |
| 予定だけ取消 | 1 | 0 | 0 | 停止未完了 |
| 全対象を停止、検査は1分前に正常終了 | 0 | 0 | 0 | 停止完了、検査正常 |
| 全対象を停止、検査は1分前に失敗 | 0 | 0 | 0 | 停止完了、検査失敗 |
| 全対象を停止、最終検査は20分前 | 0 | 0 | 0 | 停止完了、監視停止の疑い |

この試験では、最終検査が10分超なら監視停止を疑います。
停止完了は、担当・予定・新規処理が全て0の条件です。
停止の成否と、検査結果の正常・失敗・古さを別に答えます。

- 判定の一致が5件中5件なら合格です。
- 最初の2件を停止完了とする誤判定は、2件中0件が条件です。
- 検査失敗と監視停止の疑いは、2件中2件の検出が条件です。
- 不一致があれば、対象の一覧か判定条件を直して5件を再判定します。

これは停止を判断する手順の試験です。
実際に停止できたことや、停止までの時間の証明にはなりません。

実際の停止操作は、将来の許可された試験だけで行います。
今回は、実行中の担当や予定を変更していません。
