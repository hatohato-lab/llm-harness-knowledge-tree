## 1. 要点（一言と、根拠の段階と、使いどころ）

自動化を始める前に、実行経路と請求先を結び付けます。

根拠の段階：公式で確認。
認証情報の選択順と、実行環境による違いを確認しました。
私の認証設定と請求先は、未確認です。

認証とは、使う人や契約を確かめる仕組みです。
APIとは、ソフトウェアが機能を呼び出す窓口です。
APIキーとは、その窓口を使うための秘密の認証情報です。
従量課金とは、使った量に応じて支払う方式です。

賢いモデルにも軽いモデルにも使います。
指示は、実行場所、認証方法、支出上限を具体化します。
定期処理や、人が対話しない長時間実行に向きます。

## 2. 仕組み（なぜ効くか）

同じ製品でも、認証経路が違えば請求先が変わり得ます。
月額契約でログイン済みでも、別の認証が優先され得ます。
対話画面の状態だけで、自動実行の請求先は決まりません。

Claude Codeの `-p` は、人と対話しない実行方式です。
公式文書では、この方式は設定済みのAPIキーを使います。
ただし、接続先や管理設定の優先関係も確認が必要です。
クラウド会話は、ローカル実行と認証規則が異なります。
詳細は[公式の認証文書](https://code.claude.com/docs/en/authentication)で確認できます。

さらに、外部の実行基盤にも料金があり得ます。
モデル利用料だけで、自動化全体の費用とはしません。
「定額だから無制限」は、契約の裏付けが必要です。

## 3. 使い方（手順と例）

1. 対話、定期実行、クラウド会話を分けて書きます。
2. 各経路の認証方法と契約の種類を確認します。
3. 秘密の値を出さず、設定の有無だけを調べます。
4. 有効な認証表示を、公式の優先順位と照合します。
5. モデル利用料と外部基盤の費用を分けます。
6. 各経路の上限と、停止を確認する場所を記録します。

記録の例です。

| 欄 | 書くこと |
|---|---|
| 実行経路 | 手元の対話、無人実行、クラウド会話 |
| 有効な認証 | 月額ログイン、APIキー、外部基盤など |
| 請求先 | 契約の区分と、確認した表示 |
| 上限 | 作業、日、月の制限と、対象範囲 |
| 別料金 | 実行基盤、保存先、外部道具 |
| 確認日 | 文書と表示を照合した日 |

PowerShellとは、文字の命令で操作する道具です。
秘密の有無だけを見るPowerShellの例です。
これは存在確認であり、請求先の証明ではありません。

```powershell
Test-Path Env:ANTHROPIC_API_KEY
```

認証の値そのものを、報告や台帳へ貼らないでください。
確認後も、認証設定を自動で変更する必要はありません。

## 4. 試し方（最初の一歩と測り方）

最初は30分で、架空の3経路を公式文書と照合します。
これは認証と請求の取り違えを見つける机上試験です。
モデルの呼出し、認証変更、課金は行いません。

1. 5分で、下の表の「照合する認証」を隠して予想を書きます。
2. 15分で、[公式の認証優先順位](https://code.claude.com/docs/en/authentication#authentication-precedence)と照合します。
3. 10分で、3件の正誤、根拠のURL、残る未確認点を記録します。

| 架空の経路と前提 | 照合する認証 |
|---|---|
| ローカルの `-p`。APIキーあり。より優先される接続先・認証・管理設定はなし | APIキー側 |
| ローカルの `-p`。有効な月額ログインのみで、他の認証情報はなし | 月額ログイン側 |
| クラウド会話。環境にAPIキーも置かれている | クラウド会話の月額ログイン側 |

合格は、認証の予想が3/3件一致し、未確認の請求額を断定した件数が0件です。
3件と30分は、この葉の練習用の目標であり、提供元の実測値ではありません。
判定できない場合は未確認と書き、無人実行を始めない条件にします。
この試験の合格は、私の実際の請求先や請求額の確認ではありません。
公式の注意書きは、過去の予告と現行条件を分けます。

将来の許可済み試行では、小課題一件だけを動かします。
予定した請求先と、利用明細の計上先を照合します。
違った場合は、自動実行を増やす前に原因を調べます。
本調査では、認証情報の取得や課金試験は行っていません。

請求先が未確認の経路数と、予定との差が出た件数を測ります。
