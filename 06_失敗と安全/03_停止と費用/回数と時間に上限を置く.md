## 1. 要点（一言と、根拠の段階と、使いどころ）

成功条件とは別に、回数と時間で打ち切る上限を置きます。

- 根拠の段階：公式で確認。
- 上限の機能は確認済みです。品質改善の幅は未確認です。
- 賢いモデルでも、軽いモデルでも使えます。
- 指示は具体的にします。数える単位と上限を明記します。
- 長い調査、修正の反復、担当を増やす作業に向きます。

反復は、試行と確認を繰り返すことです。
非対話実行は、依頼を一度渡して結果を受け取る方法です。
深さは、主担当から下に続く担当の階層数です。

## 2. 仕組み（なぜ効くか）

終了を自己判断だけに任せると、終わらない場合があります。
実行側の上限なら、説明の巧さとは別に打ち切れます。
Anthropicは、最大反復数などの停止条件を勧めます。
[公式の設計指針](https://www.anthropic.com/engineering/building-effective-agents)

Claude Codeの `--max-turns` は非対話実行用です。
上限に達するとエラーで終わります。既定の上限はありません。
新しい入力には新しい上限が付く場合があります。
[公式の実行引数](https://code.claude.com/docs/en/cli-reference)

深さ、同時に動く数、全期間の起動数は別です。
深さだけを絞っても、横に増やす動きは残ります。
再開による同時数超過もあるため、全体の台帳を持ちます。
[公式の担当制限](https://code.claude.com/docs/en/sub-agents#concurrent-subagent-limit)

停滞は、合格項目や新しい証拠が増えない状態です。
回数が残っていても、同じ失敗の反復は別に止めます。
文章量やファイル数だけの増加は、進歩に数えません。
一回が長い処理には、回数とは別の時間制限が必要です。

Google ADKは、担当と処理を組み立てる開発用の道具です。
LoopAgentは、担当を決めた順で繰り返す実行部品です。
終了通知か最大反復数で止める構成を、元葉で確認しています。
順番と上限を担当の外側に置く実現例として扱います。
[ADKの反復制御](https://adk.dev/agents/workflow-agents/loop-agents/)
今回、[本体の反復条件](https://github.com/google/adk-python/blob/main/src/google/adk/agents/loop_agent.py)も読みました。
回数との比較と終了通知の判定を、コード上で確認しました。
本体にはLoopAgentの非推奨化の注記があります。
ここでは上限を外側で扱う機構の例とし、新規導入の推奨にはしません。
コードを読んだ確認であり、動作試験ではありません。

WebSearchは、Claude Codeに組み込まれた検索機能です。
元葉では、親と補助担当で共有する検索枠を確認しています。
確認時の既定値は200回で、契約の利用枠とは別です。
既存資料で答えられる問いを除き、必要な検索へ配ります。
回数の変更や上限到達の動作は、まだ試していません。
[検索機能の回数枠](https://code.claude.com/docs/en/tools-reference#session-search-limit)

## 3. 使い方（手順と例）

以下は設計例です。数値の最適性と効果は未確認です。

1. 完了条件を、成果物で判定できる一文にします。
2. 一回を「仮説一つの確認」などに固定します。
3. 回数、経過時間、担当の深さ、総起動数を決めます。
4. 再開しても、作業全体の残り上限を引き継ぎます。
5. 上限後は未完了の理由と、確認済みの成果を残します。
6. 目的や許可期限の変更は、人の判断へ戻します。

```text
資料の矛盾を一件調べます。
一回は、仮説一つと根拠の照合です。
三回または20分で、新しい探索を止めます。
最後の二分は、成果と未確認点の保存に使います。
再開時も、この課題の累計をゼロへ戻しません。
目的と許可期限を、自分で変更しないでください。
```

この文章だけで、厳密な時間制限は保証されません。
自動化では、実行を管理する側にも時間上限を置きます。

`/goal` は、条件へ向けて作業を続けるClaude Codeの機能です。
その文章に書く回数上限は、会話を読むモデルが判定します。
機械的な回数制限とは区別します。
再開時に回数と時間の基準が戻るため、累計を別に残します。
[公式の目標と再開](https://code.claude.com/docs/en/goal)
許可された保存処理のために、終了前の余裕を残します。

文脈は、モデルが今の判断に使える情報です。
文脈の使用率を、保存の通知へ使う派生案もあります。
投稿の50%通知・60%停止は、公式の基準ではありません。
比較試験と実装は未確認です。
全道具を止めると、引継ぎ記録も保存できません。
まず通知だけで、保存漏れが減るかを確かめます。

保存投稿には、子一体が孫六体を起動した体験談があります。
また、重複した処理の再起動で記録が増えた報告もあります。
記録で保存容量が埋まり、複数のサービスが止まったといいます。
どちらも体験談だけで、実際の実行記録は未確認です。

対策案では、親子を通じた総起動数と再起動回数を数えます。
再起動しても、作業全体の上限をゼロへ戻しません。
記録量と空き容量にも、警告と新規起動を止める基準を置きます。
これは本資料の提案です。効果は未実証です。

終了時は、最良の確認済み結果と残課題を保存します。
失敗した案、新しい証拠、累積量、再開条件も残します。
上限の警告と、実行を止める境界を別に決めます。

| 終了理由 | 残す記録 | 次の扱い |
|---|---|---|
| 達成 | 成果物と確認結果 | 完了とする |
| 停滞 | 同じ失敗と試した案 | 前提を調べ直す |
| 上限 | 累積量と残件 | 続行の条件を確認する |
| 外部待ち | 不足情報と必要な判断 | 条件が整うまで保留する |
| 解消不能 | 実現できない条件と根拠 | 未完了として条件の見直しへ戻す |

例えば、文書修正は最大3回という仮上限を置きます。
合格項目が2回続けて増えなければ、停止候補にします。
この回数は練習用で、最適値の主張ではありません。
探索では、新しい証拠の獲得も進展として記録します。
詳しい判定は[進歩のない反復を打ち切る](進歩のない反復を打ち切る.md)へ進みます。

## 4. 試し方（最初の一歩と測り方）

最初の40分は、次の6例を紙上で判定します。
上限は累計3回または20分とし、再開しても累計を引き継ぎます。
最初の5分で表を写し、期待する判定の列を隠します。
次の20分で続行・停止と理由を書き、最後の15分で照合します。

| 例 | 現在の状態 | 期待する判定 |
|---|---|---|
| A | 2回、10分、未達 | 次の1回へ進む |
| B | 3回、12分、未達 | 回数上限で停止 |
| C | 2回、20分、未達 | 時間上限で停止 |
| D | 再開前2回＋再開後1回、12分、未達 | 累計3回で停止 |
| E | 1回、8分、許可期限切れ | 期限切れで停止 |
| F | 2回、10分、完了条件を達成 | 達成して終了 |

各例で、累計回数、時間、終了理由、残件を一行にまとめます。
合格値は、判定と理由の一致6/6、記録の完成6/6です。
B〜Eの4例で新規開始を許す判断は0件、未達の成功扱いも0件です。
数字はこの葉の練習案で、提供元の実測値ではありません。
合格しても分かるのは判断表の整合性だけです。
自動実行の停止、時計の精度、子担当の停止は未検証です。

後日の無害な動作試験では、上限後の開始数も実際に数えます。
深さ、同時数、総起動数、早すぎる停止を別々に記録します。
今回は自動実行、設定変更、課金を伴う試行をしていません。
