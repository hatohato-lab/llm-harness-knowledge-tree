## 1. 要点（一言と、根拠の段階と、使いどころ）

返答の終了、作業の成功、人の入力待ちを分けて表示します。

根拠の段階：公式で確認。

状態は、ある時点で確認できた作業の状況です。
フックは、決めた出来事の前後に処理を動かす機能です。
背景作業は、主担当の会話と並行して動く処理です。

賢いモデルでも軽いモデルでも、状態の一覧を使います。
状態の名前、更新条件、根拠を具体的に指定します。
軽いモデルには、記録からの定型集計を任せられます。
賢いモデルには、複数担当の矛盾した状態を点検させます。
並行作業、長い処理、定期収集に向く設計です。
この役割分担の効果は未測定です。

## 2. 仕組み（なぜ効くか）

画面が静かなだけでは、実行中か入力待ちか分かりません。
状態と確認時刻があれば、次に誰が動くかを判断できます。
表示が更新されない時は、状態不明として扱えます。

公式では、許可要求と応答後の待機を異なる通知型で分けられます。
idle_promptだけでは、追加の入力要求があるとは決めません。
Stopは、主担当が返答を終えた時の出来事です。
作業全体の成功を意味するものではありません。
[公式の通知](https://code.claude.com/docs/en/hooks#notification)、
[公式のStop](https://code.claude.com/docs/en/hooks#stop)

道具の失敗には、別の出来事が用意されています。
会話の終了と、道具の終了も別に扱います。
[公式の出来事一覧](https://code.claude.com/docs/en/hooks#hook-events)

取得件数ゼロでも、取得自体が失敗したかもしれません。
また、前日の入力で当日の収集を済ませたとは言えません。
当てはめ資料は、取得結果と日付を分けて確かめる案です。
これは監視漏れを減らす設計で、効果は未測定です。

## 3. 使い方（手順と例）

1. 作業と担当に、それぞれ区別できる番号を付けます。
2. 状態の名前と、更新してよい根拠を決めます。
3. 状態、確認時刻、根拠、次の行動を一表にします。
4. 主担当と背景作業の状態を、別々の行に残します。
5. 返答後に、未完了の担当が残っていないか確かめます。
6. 記録が古い、または欠けた場合は、状態不明にします。

最初は、次のような表で十分です。

| 状態 | 更新の根拠 | 次の行動 |
| --- | --- | --- |
| 実行中 | 対象の処理開始を確認 | 結果を待つ |
| 許可待ち | 確認要求を確認 | 人が範囲を判断 |
| 入力待ち | 追加の入力要求を確認 | 必要事項を返す |
| 返答終了 | 返答が終わった | 成果物を確認 |
| 失敗 | 対象の失敗結果を確認 | 原因を読む |
| 中断 | 人の停止や時間切れを確認 | 再開条件を確認 |
| 成功確認済み | 成果物と条件が一致 | 完了として報告 |
| 状態不明 | 根拠が欠けるか古い | 現在の状態を再確認 |

定期収集では、次の欄も追加します。

| 項目 | 例 |
| --- | --- |
| 取得結果 | 成功、失敗、未確認 |
| 取得件数 | 0件、3件など |
| 入力の日付と版 | 前日分、当日分、資料の版 |
| 確認時刻 | 実際に確認した時刻 |
| 判定 | 新着ゼロ、取得失敗、古い入力 |

「新着ゼロ」は、取得成功を確かめた後だけ使います。
古い入力を使った場合は、その日付を明示します。
失敗を新着ゼロに置き換えて、作業済みにしません。

通知は、人の入力が必要な状態から少数で始めます。
本文や秘密を通知へ入れず、手元の一覧を開きます。
音が鳴ったことだけで、成功とは判定しません。

会話記録の保存は、出来事の発生より遅れる場合があります。
直後の記録欠落だけでは、成功にも失敗にも決めません。
[公式の共通入力](https://code.claude.com/docs/en/hooks#common-input-fields)

## 4. 試し方（最初の一歩と測り方）

最初の一歩は、45分の机上試験です。
AIの追加実行、通知の送信、設定変更は不要です。
以下の数値目標は、この葉の試験案であり、提供元の実測値ではありません。

5分で下の八件を用意し、判定欄を隠します。
15分で状態と次の行動を書き、15分で正解欄と照合します。
最後の10分で間違った条件を直し、同じ八件を再採点します。

| 架空の証拠 | 正解となる判定と次の行動 |
| --- | --- |
| 操作の許可要求が出ている | 許可待ち。人が範囲を判断する |
| 不足する情報について明示的な質問がある | 入力待ち。必要事項を返す |
| 主担当のStopと、実行中の背景担当がある | 主担当は返答終了、背景担当は実行中。結果を待つ |
| 取得失敗と件数0が記録されている | 失敗。原因を確認する |
| 当日入力で取得成功、件数0である | 新着ゼロ。確認日を残す |
| 取得成功だが入力は前日分である | 古い入力。当日分を確認する |
| 保存成果物が合格条件と一致している | 成功確認済み。完了を報告する |
| 状態の根拠と確認時刻がない | 状態不明。現在の状況を確認する |

合格は、状態と次の行動の組が8件中8件正しいことです。
取得失敗を新着ゼロ、前日入力を当日分、背景作業中を全体成功、
根拠なしを成功とした誤りは、それぞれ1件中0件を必須とします。
各件の判定時間も測り、最長2分以内を目標にします。
通知は実際に送らず、「人へ知らせる」の印を最初の二件だけに付け、
必要な印の漏れ0/2件、ほかの六件への不要な印0/6件を数えます。
これは分類ルールの試験で、実機の通知時間や漏れを実測するものではありません。
この葉では、通知設定の導入や変更は行っていません。
