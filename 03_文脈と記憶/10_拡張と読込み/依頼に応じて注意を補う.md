## 1. 要点（一言と、根拠の段階と、使いどころ）

依頼の内容を見て、その場で必要な注意や状態だけを足す。
根拠の段階：公式で確認。

フックは、特定の出来事を合図に動く処理である。
追加文脈は、元の依頼に添える補足情報である。

対象分野や現在の状態で、読むべき注意が変わる資料調査やコードレビューに向く。
対象は、Claude Code上で補足文脈を受け取る、推論型または軽量の対話モデルである。
推論型には、目的・関係する事実・参照先を短く渡す。
軽量型の試行では、適用する語句・対象・返す補足の例まで指定する。
この指示の分け方は試行案であり、モデル間の優劣を示す実測ではない。
抽象的な心構えだけを毎回足す用途には向かない。
変わらない共通規則は、常設の指示に置く。

## 2. 仕組み（なぜ効くか）

UserPromptSubmitは、依頼を処理する直前の出来事である。
ここで依頼に合う補足を選び、モデルへ渡せる。
元の依頼は残り、補足が隣に加わる。
[公式の送信時フック](https://code.claude.com/docs/en/hooks#userpromptsubmit)

必要性を判定してから情報を入れる点が、この型の中心である。
文書に適用条件を書くだけの型とは、読込みの時点が異なる。
対象外なら何も足さず、関係する場合だけ短く足す。
読取量と注意の適合度を両方測る設計にする。
この効果の大きさは、私の環境では未確認である。

basemodeは、作業の知識を検索して補う外部ソフトである。
作者は、依頼に合う規則や過去の判断を渡す方式を示している。
開始時や道具実行時にも、別の情報を渡す。
同じ型の実装例であり、導入の必須条件ではない。
[作者の仕組みの説明](https://github.com/ChristopherKahler/base)

## 3. 使い方（手順と例）

次は試行用の設計案である。今回は登録していない。

1. 最近、繰り返して補った注意を一つ選ぶ。
2. 必要な依頼と、不要な依頼を具体例で分ける。
3. 条件に合う時だけ、一つの短い補足を返す。
4. 古い状態が混ざらないよう、観測時刻を添える。
5. 元の指示との重複と矛盾を確認する。

JSONは、項目名と値を組にして書くデータ形式である。
`additionalContext` は、追加文脈を渡す項目名である。
条件に合った時に返すJSONの例を示す。
判定処理とフックへの登録は、別途必要である。

```json
{
  "hookSpecificOutput": {
    "hookEventName": "UserPromptSubmit",
    "additionalContext": "この調査の原典一覧は sources.md にある。"
  }
}
```

同じ情報が常設の指示にあれば、追加しない。
毎回の長文補足は、文脈量と待ち時間を増やす。
補足による行動の遵守は保証されない。

送信時フックは、人が打つ依頼以外でも動く場合がある。
定期処理や、別担当からの報告も試験対象に含める。
再開時には、過去に足した状態が古くなる場合もある。
[発火条件と追加文脈の扱い](https://code.claude.com/docs/en/hooks#add-context-for-claude)

## 4. 試し方（最初の一歩と測り方）

最初の一歩は30分の紙上試験とする。フックの登録やモデル呼出しは不要である。
10分で、対象の依頼3件と対象外の依頼3件、期待する補足の正解表を作る。
次の10分で、条件文だけを使って6件を判定し、返す補足を記入する。
最後の10分で、正解表との一致数、誤発火数、追加文字数を数える。
成功の目安は、必要な3件すべてに適切な補足が付き、対象外への追加が0件、1件の補足が120字以内である。
これは条件設計の合格基準であり、実際の行動改善を示す数値ではない。
その後に本体試験を行う場合は、同じ調査依頼3件で補足の有無を比較し、出典漏れの減少件数も測る。

| 項目 | 測る内容 |
| --- | --- |
| 適合 | 必要な依頼に補足が付いたか |
| 誤発火 | 不要な依頼に補足が付いた数 |
| 量 | 一回と会話全体の追加文字数 |
| 品質 | 補足の有無で、出典漏れが減ったか |
| 鮮度 | 再開後も状態が正しいか |

文脈へ届いたことと、行動が改善したことを分けて測る。
補足だけでは改善しないなら、条件か内容を見直す。
効果がない補足は、採用候補から外す。
