## 1. 要点（一言と、根拠の段階と、使いどころ）

対象のファイルを扱う時だけ、専用の規則を読ませます。

根拠の段階：公式で確認。

推論を重ねるモデルにも、小型で高速なモデルにも、同じパス条件を適用して試せます。
読込みを制御する仕組みなので、モデル別の品質改善幅は別途測ります。
指示は対象の場所と動作を具体的に書きます。
種類の違う資料やコードが混在する作業に向きます。

## 2. 仕組み（なぜ効くか）

規則とは、繰り返し守ってほしい短い指示です。
文脈とは、モデルが現在の判断に使う情報です。
pathsは、規則を読む対象のファイル名を指定する欄です。

専用の規則を必要な場面に絞ると、文脈の混雑を減らせます。
読込条件の根拠は、[公式の対象別規則](https://code.claude.com/docs/en/memory#path-specific-rules)です。
規則をファイルへ分けるだけでは、読取量は減りません。
pathsがない規則は、起動時に読み込まれます。
Read、Write、Editは、読取り・保存・編集の道具です。
対象はRead、Write、Editで扱うファイルです。
すべての道具の使用で発動する設定ではありません。

条件の読込みは機械が決め、本文への対応はモデルが判断します。
読込みの成功は、そのまま遵守の成功にはなりません。
減る量や誤りの改善率は、課題ごとに未確認です。

## 3. 使い方（手順と例）

1. すべての作業に必要な規則を分けます。
2. 特定の種類にだけ必要な規則を一枚にします。
3. 対象の相対パスを、冒頭のpathsへ書きます。
4. 対象になる例と、ならない例を用意します。
5. 別々の新しい会話で、両方を開いて確かめます。

YAMLは、項目名と字下げで設定を表す書式です。
次は、この葉で作った練習用の規則です。
置き場所の例は、.claude/rules/report.mdです。

```yaml
---
paths:
  - "reports/**/*.md"
---
# 調査報告
比較表には、対象が分かる題名を付ける。
```

星印は、複数のファイル名をまとめて指定する記号です。
対象例はreports/week1.mdです。
対象外の例はnotes/week1.mdです。
設定の書式が壊れると、条件なしで読まれる場合があります。
独自の優先度欄を加えても、公式の制御にはなりません。

## 4. 試し方（最初の一歩と測り方）

最初は30分の試行案です。準備10分、二会話での確認10分、採点10分に分けます。
対象文書一枚と対象外文書一枚を、同じモデル・版の新規会話で一回ずつ扱います。
合格は対象側の読込み1/1回、対象外側の読込み0/1回、対象側の題名付与1/1回です。
対象外で専用規則に従ったと判断できる出力は誤適用として数え、0件を目標にします。
使用量だけの増減を合否にせず、読込欄を確認できない試行は未確認に残します。

最初は、規則一枚と架空の文書二枚だけで比べます。
読込み確認には、使用量を表示する/contextを使います。
Memory files欄と、実際の表の題名を別々に確認します。

記録するのは、読込みの有無、使用量、誤適用の件数です。
対象外でも一度読んだ規則が残る影響を避けます。
そのため、比較ごとに新しい会話を使います。

- 確認の限界：
  - 短縮URLの転送先を確認したという意味ではありません。
  - 別経路のQiita記事は再取得も失敗したため、本文の根拠には追加しません。
  - 調査では取得失敗です。
  - 本文はこの調査で未確認です。
  - 元のURLがない投稿は、対応先が未確認です。
  - ほかにも、確認できていない点が複数あります。
