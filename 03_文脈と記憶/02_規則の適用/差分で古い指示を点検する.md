## 1. 要点（一言と、根拠の段階と、使いどころ）

古い条件や矛盾を探し、変更案を見てから直します。

根拠の段階：公式で確認。

推論を重ねるモデルでは複数規則の照合、小型で高速なモデルでは二文の比較から試します。
これは試行範囲の決め方で、モデル間の優劣を測った結果ではありません。
指示は対象ファイル、確認項目、返す形式まで具体化します。
モデルの更新後や、常設指示が増えた時に向きます。

## 2. 仕組み（なぜ効くか）

監査とは、指示の古さや矛盾を根拠付きで点検することです。
差分とは、変更前と変更後の違いを示したものです。

常設指示は、昔の条件を現在へ持ち込むことがあります。
同じ判断に相反する規則があると、適用が不安定になります。
この競合の説明は、[公式の指示の書き方](https://code.claude.com/docs/en/memory#write-effective-instructions)に対応します。
原文と現行の条件を比べ、矛盾の原因を分けて考えます。
削る行数を先に決めず、必要な判断が残るかを確かめます。

公式の監査は、存在しない参照先や古い指示も調べます。
提案を報告し、適用を求めるまではファイルを変えません。
ただし、指摘自体の正しさは原文で確かめる必要があります。

例外や撤回が抜けると、古い指示も有効に見えます。
長文の入力自体が欠けた場合は、保存された入力も照合します。
書式の機械検査と、意味の矛盾を調べる監査は区別します。
監査がすべての矛盾を見つけることは、保証されません。

## 3. 使い方（手順と例）

1. 対象の指示ファイルを一枚か二枚に限定します。
2. 現在の作業条件と、残したい規則を列挙します。
3. 古い参照先、重複、矛盾、撤回漏れを報告させます。
4. 該当箇所を開き、根拠と修正案を見比べます。
5. 必要な変更だけを採用し、小課題で確かめます。

監査の呼出し例です。今回、実行はしていません。

```text
/doctor prompt-audit .claude/rules/report.md
報告だけを作り、ファイルは変更しない。
該当行、食い違い、最小の修正案を示す。
正しい方を決められない時は、未確認と書く。
```

この呼出しは、Claude Code 2.1.283以降に対応します。
対象を省略すると、個人用の指示まで監査対象が広がります。
内蔵のclaude-api手順が無効な場合は利用できません。
古い版向けという理由だけで、必要な制約を消しません。

使ったモデルと版、該当行、保つ制約も差分へ添えます。
必要な安全規則は、古い日付だけを理由に外しません。
安全規則の試行は、無害な例と操作記録で確かめます。

同じ監査には、別名の `/checkup prompt-audit` もあります。
`/claude-api prompt-audit` は、別の入口です。
後者は、公式ではv2.1.221以降とされています。
連結した `/claude-api-prompt-audit` という名前は未確認です。
これらの版と入口は、統合元の公式確認記録に従います。

## 4. 試し方（最初の一歩と測り方）

最初は40分の試行案です。準備10分、監査10分、修正案と採点20分に分けます。
架空の規則だけを使い、正解表には下記二件と「残す重要条件二件」を先に書きます。
合格は検出2/2件、誤検出0件、重要条件の欠落0/2件、対象外読取り0件です。
時間内に終わらない場合は未完了とし、検出成功へ数えません。

架空の規則二枚に、矛盾一件と古い参照一件を作ります。
対象を限定して、二件を見つけられるか確認します。
検出数、誤検出数、根拠の行、対象外の読取りを記録します。
修正後は、必要な条件の欠落も数えます。
時間や費用が減るという効果は、別途測定が必要です。

矛盾のない重要条件と、適用範囲が違う規則も一組置きます。
違反数と手直し時間を、修正前後の同じ課題で比べます。
読めた回数と守った回数は、別欄に残します。
適用機会がなかった規則は、遵守したと数えません。
