## 1. 要点（一言と、根拠の段階と、使いどころ）

別のプログラムへ渡す答えは、項目と値の種類を定義する。

JSONは、項目名と値で情報を表す書式である。
JSON Schemaは、JSONの項目や値の種類を決める規則である。
構造化出力は、その規則に合わせて回答の形を制約する機能である。

- 根拠の段階：公式で確認
- 対象は構造化出力に対応する汎用モデルと軽量モデル。
  例はClaude Sonnet 4.6とHaiku 4.5で、[公式の対応表](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#compatibility)に両方がある。
- 指示の細かさは、必須項目・型・選択肢・余分な項目の禁止まで定義する。
  「確認済み」にする根拠と資料不足時の扱いは、別の文で伝える。
- 使いどころは、情報抽出、分類、集計へ渡す定型データである。

## 2. 仕組み（なぜ効くか）

[公式の仕組みの説明](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#why-use-structured-outputs)では、規則に合う生成だけを選ぶ制約付き生成で、必須項目や型をそろえる。
文章で「JSONで答えて」と頼むだけでは、形式を外す余地が残る。
生成できる形を制限するため、後のプログラムが期待する項目を読み取りやすくなる。

形が正しくても、値の事実性や分類の正しさは別問題である。
拒否や出力上限による中断では、形が完成しない場合もある。
使える規則には制限があり、利用経路でも扱いが異なる。
例えば、[Claude Codeの説明](https://code.claude.com/docs/en/headless#get-structured-output)では、JSON Schemaの`format`は注釈として扱われ、強制されない。

## 3. 使い方（手順と例）

1. 後の処理が必要とする項目を最小限に絞る。
2. 各項目の意味と、不明な値の扱いを決める。
3. 対応する構造化出力の設定へ規則を渡す。
4. 受け取る側で、終了状態と内容を別々に確認する。

次は、主張と確認状態を受け取るための設計例である。
外部サービスを呼び出す命令ではない。

```json
{
  "type": "object",
  "properties": {
    "claim": {"type": "string"},
    "status": {
      "type": "string",
      "enum": ["確認済み", "未確認"]
    }
  },
  "required": ["claim", "status"],
  "additionalProperties": false
}
```

項目の意味は、別に短く指示する。

```text
claimには、資料に明記された主張を書いてください。
statusは、指定の根拠を確認できた時だけ「確認済み」です。
本文がない時は、claimを空文字にし「未確認」とします。
```

Claude Codeの通常JSON出力には、実行情報も含まれる。
規則に合う結果は、`structured_output`から読む。
APIは、プログラムからサービスを呼ぶための窓口である。
Claude APIでは、`output_config.format`へ規則を渡す。
二つの設定名を、同じ呼び出しへ混ぜない。

## 4. 試し方（最初の一歩と測り方）

最初の一歩は、外部送信なしでできる45分の規則と採点の練習にする。
時間と合格条件はこの葉の検証案であり、モデルの性能値ではない。

1. 10分で「開始時刻を抽出する」架空入力を三件作る。「指定資料に開始10時と明記」「開始時刻の記載なし」「本文なし」とする。この練習では開始時刻がない場合も空文字・未確認と指示し、正解は順に`{"claim":"開始10時","status":"確認済み"}`、`{"claim":"","status":"未確認"}`、`{"claim":"","status":"未確認"}`とする。
2. 10分で六つの回答を用意する。正解3件に加え、`status`の欠落、選択肢外の`status`、本文なしなのに「確認済み」という誤答を各1件作る。
3. 15分で、第3節の規則に照らして六件を手で採点する。「必須2項目がある・両方文字列・statusが2択・余分な項目なし」を形式、「資料と一致する」を内容の検査にする。
4. 10分で採点結果を正解と比べる。合格は6件中6件を正しく判定し、形式違反2件と、形式は正しいが内容が誤る1件を区別できること。

この練習は判定基準の点検であり、モデルの生成制約が働くことの実測ではない。
後にモデルで比較する時は、同じ入力三件と内容の指示を使い、同じモデル・設定、毎回新しい会話で、文でJSONを求める条件とSchemaを渡す条件を各一回実行する。計6回答の形式違反数と内容誤り数を分ける。
中断や拒否も通常の成功結果に数えず、別に記録する。
今回は実モデルを呼ばず、第6節は未実施のまま保つ。
