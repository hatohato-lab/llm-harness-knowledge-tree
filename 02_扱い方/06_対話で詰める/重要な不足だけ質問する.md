## 1. 要点（一言と、根拠の段階と、使いどころ）

結論を変える不足だけ、作業前に質問させる。

- 根拠の段階：公式で確認
- 推論型モデルには、「回答で結論が変わる場合」という質問条件を渡す。
- 低遅延の軽量モデルには、読み手・場面・完成条件の確認項目と質問の形を渡す。
- 使いどころ：新機能、調査依頼、説明文の作成。

モデル別の使い分けは、ここで試すための案である。

ここでいう不足は、資料で決まらない目的や好みである。
質問数を増やすこと自体は目的にしない。
小さく明確な修正なら、そのまま頼んでよい。

## 2. 仕組み（なぜ効くか）

曖昧さとは、同じ依頼に複数の解釈が残る状態をいう。
質問への返答で、採るべき解釈を絞れる。
ただし、すべての不足を人に尋ねると時間がかかる。
資料で分かる事実と、本人の選択を分けるのが要点である。
この区別は、事実を自分で調べ、判断を本人に尋ねる[grillingの指示本文](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/grilling/SKILL.md)に対応する。
資料で解ける質問を省き、回答で変わる判断へ絞ることが、質問の負担を抑えるという設計上の説明である。

Claude Code公式は、大きな機能の事前聞き取りを勧める。
実装方法や見落とした条件を尋ねる例がある。[公式](https://code.claude.com/docs/en/best-practices#let-claude-interview-you)

研究では、質問する場面、質問内容、回答利用を分けている。
質問を向ける対象の選び方も、結果に影響した。
これは、毎回質問すればよいという結果ではない。
私の作業で同じ効果が出るかは未確認である。[論文](https://arxiv.org/abs/2311.09469)

## 3. 使い方（手順と例）

1. 本人が、望む完成状態を一文で伝える。
2. 読める資料を示し、事実は先に調べさせる。
3. 回答で結論が変わる点だけ、質問させる。
4. 一つ決めたら、その答えを次の質問へ反映させる。
5. 重要な未決事項がなくなったら、聞き取りを終える。

推論型モデルには、次の程度から始める。

```text
目的は、初めて使う人が迷わない説明書を作ることです。
まず添付の説明書と画面を確認してください。
資料では決められず、結論が変わる点だけ質問してください。
一回に一つ聞き、何の判断に必要かを添えてください。
すでに決まったことは、聞き直さないでください。
```

低遅延の軽量モデルには、確認する場所を具体化する。

```text
読み手、使う場面、完成時の状態を点検してください。
資料に答えがある項目は、その答えを書いてください。
答えがない項目のうち、説明内容が変わる一つを聞いてください。
不明点がなければ「質問不要」として草案へ進んでください。
```

理解を確かめたいときは、逆に人から質問してもよい。
「この機能はどこで使うか」と、場所や経緯を尋ねる。
改修へ進む前に、根拠のある説明かを確認する。
公式にも、既存コードへ直接質問する例がある。[公式](https://code.claude.com/docs/en/best-practices#ask-codebase-questions)

## 4. 試し方（最初の一歩と測り方）

最初の一歩は、説明書1件を使う計50分の比較案である。
時間配分と以下の合格条件は、この葉の検証用の仮基準である。

1. 準備10分：手元の説明書500字以内を選び、読み手・使う場面・完成条件を本人が3件決める。資料には1件だけ書き、残り2件は質問されたら答える。同じモデルと設定を使い、両方式とも本文400字以内にそろえる。
2. 比較Aに10分：新しい会話で質問なしの草案を作り、必要な手直しまで行って所要時間を記録する。
3. 比較Bに10分：別の新しい会話に同じ資料と第3節の指示を渡す。質問は最大3回とし、必要な手直しもこの時間内に行う。
4. 採点15分：各方式の最終案について3要件の充足数、資料に答えがある不要な質問数、決定済み項目の聞き直し数を数える。
5. 記録5分：質問への回答と手直しの合計分数を両方式で比べる。生成待ちを含め時間枠を超えたら打ち切る。

実施順はくじで決め、順番も記録する。一方の回答を他方の会話へ持ち込まない。
比較Bが要件3/3件、不要質問と聞き直しが各0件を満たし、回答と手直しの合計が比較A以下なら今回は合格とする。
比較Aも3/3件で時間差がなければ改善は未確認とする。モデルと資料、本文の長さをそろえ、一件の結果を一般化しない。
