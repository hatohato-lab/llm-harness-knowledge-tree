## 1. 要点（一言と、根拠の段階と、使いどころ）

fast mode は、対応する Opus の出力を速くする設定です。
effort は、モデルが仕事へ割く量の目安です。
利用クレジットは、契約枠外の利用に使う有料残高です。

**速い出力が欲しいのか、考える量を減らすのかを分けます。**

- 根拠の段階：本体と公式で確認
- 使いどころ：対応する Opus 5.5・5・4.8で、小さな画面修正や対話しながらの不具合調査に使います。
- 指示の抽象度：目的に加え、変更する箇所、変えない操作、合格条件を具体的に示します。速さの比較では同じ指示文を使います。
- 軽いモデル：Sonnet・Haiku は fast mode の対象外です。軽いモデルへの変更は別の比較にします。

## 2. 仕組み（なぜ効くか）

[公式の fast mode と effort の比較](https://code.claude.com/docs/en/fast-mode#fast-mode-vs-effort-level)は、fast mode を同じモデルの高速な構成と説明します。
モデルの能力を保ち、速さを優先する設定です。
一方、effort を下げると、考える量が減る場合があります。
こちらは難しい課題で、品質との交換が起き得ます。

| 選ぶもの | 変える主な点 | 比べるもの |
| --- | --- | --- |
| fast mode | 出力する速さ | 待ち時間と追加の費用 |
| effort を下げる | 仕事へ割く量 | 品質、時間、使用量 |
| 軽いモデルへ替える | 処理するモデル | 得意な作業と合格率 |

作業全体には、資料の読取りや道具の待ち時間もあります。
出力が速くても、全体が同じ割合で速くなるとは限りません。
これは測定時に分けて考えるための推測です。

## 3. 使い方（手順と例）

1. 待っている時間が、モデルの出力中かを調べます。
2. 同じモデルと effort のまま比較する計画を作ります。
3. 利用する場合は、対応モデルと料金条件を確認します。
4. 必要な対話の場面だけ、`/fast` で状態を切り替えます。

課金を伴うため、本調査では有効化も試行もしていません。
契約の残り枠とは別に、利用クレジットを使う場合があります。
現行の公式文書では、対応する Opus に限定されています。

比較する依頼の例です。

```text
この小さな画面修正を提案してください。
操作は今のままで、ボタンの位置だけを整えます。
変更案は一つに絞り、確認すべき点を示してください。
```

会話の途中で初めて有効化すると、追加の処理費用が出ます。
使うなら開始時に判断する、という公式の助言があります。
保存される設定のため、作業後の状態も確認します。

## 4. 試し方（最初の一歩と測り方）

最初の一歩は、既存の作業記録3件を使う50分の点検です。
以下の時間と判定値は、この葉の検証案です。fast の有効化や課金はしません。

1. 10分：同じ種類の小さな修正を3件選び、モデル・effort・依頼文・時刻が残っているか調べます。
2. 20分：各件の全体時間、モデルの応答待ち、道具待ちを秒で表にします。時間が重なる区間は二重に数えず、不明な区間は不明とします。
3. 10分：応答待ちの秒数÷全体の秒数を計算します。修正した箇所が正しい・操作を維持した・確認項目を示した、の3項目も各0/1点で採点します。
4. 10分：3件とも時間の80%以上を分類できれば内訳点検は合格です。品質3/3点で応答待ちが50%以上の件を fast の比較候補にします。記録不足は未判定とし、数字を補いません。

これは「速くする余地がどこにあるか」の点検で、fast の効果測定ではありません。
将来、費用を認めて比較する場合は、同じ課題3件を通常と fast で各1回、別会話で試す計画にします。
モデル・effort・指示を固定し、品質3/3点を維持して全体時間の中央値が20%以上短縮するかを判定します。
この20%も検証用の仮の基準で、公式の保証や私の実測結果ではありません。
