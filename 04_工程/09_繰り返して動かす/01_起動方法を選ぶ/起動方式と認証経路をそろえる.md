## 1. 要点（一言と、根拠の段階と、使いどころ）

無人実行の前に、起動方式と使う認証を対応させる。

根拠の段階：公式で確認

非対話実行は、会話画面を開かず指示を処理する方式です。
APIキーは、プログラムから接続するための認証情報です。
認証経路は、どのアカウントで接続するかを決める仕組みです。

使いどころ：

軽いモデルでも賢いモデルでも、起動時の確認は共通です。
指示は、実行場所と接続先と認証方式を具体的にします。
手動の処理を定期化する時や、実行環境を移す時に向きます。

## 2. 仕組み（なぜ効くか）

同じ命令でも、起動した環境で使う認証が変わります。
手動の対話画面と無人処理が、同じ契約を使うとは限りません。
公式文書には、複数の認証情報がある場合の優先順があります。
非対話実行では、設定済みのAPIキーを使う説明があります。
ただし、接続先などの上位指定も含めて照合します。
クラウド側の実行は、ローカルと別の規則があります。

ここで扱うのは、工程に合った起動構成の確認です。
料金の比較や契約選択は、この葉の対象外です。

[公式の認証優先順位](https://code.claude.com/docs/en/authentication#authentication-precedence)は、複数の認証候補から使うものを選ぶ順番を定めています。
起動方式と候補の設定名を表にすれば、手動時のログインを無人実行も使う、という思い込みを見つけられます。
この表は設定設計の点検であり、私の実際の認証経路や請求先を証明するものではありません。

## 3. 使い方（手順と例）

1. 対話、非対話、クラウドのどの方式かを決めます。
2. 接続先と、使う予定のアカウントを記録します。
3. 認証の設定名と優先順を、公式文書で照合します。
4. 失効した場合に、停止を検知する方法を決めます。
5. 導入時は、意図した経路と利用記録を照合します。

| 設計する項目 | 記録例 |
| --- | --- |
| 起動方式 | Windows側からの非対話実行 |
| 接続先 | 指定したモデル提供元 |
| 認証方式 | APIキー、または対応する契約認証 |
| 確認方法 | 有効な認証表示と利用記録 |
| 失効時 | 処理失敗として残し、別経路へ自動変更しない |

実際の経路は、設定名の存在だけでは断定しません。
秘密の値を、説明文や報告へ貼り付ける必要はありません。
bareやgh-awでは、通常の契約認証と条件が異なります。
長い無人実行では、認証の期限も予定の寿命に含めます。

## 4. 試し方（最初の一歩と測り方）

最初の一歩は、公式の該当節の読取り10分、架空の経路表作成15分、採点10分の合計35分です。
APIキーを設定した通常の非対話案と、契約ログインしか想定していないbare案の2件を紙上で比べます。
方式、接続先、認証候補、優先順位の根拠、実行可否の5欄を各案に書きます。秘密の値は使いません。
期待結果は前者がAPIキー候補、後者が認証準備不足です。上位の接続先指定がある場合は別途照合と記します。
成功基準は10欄すべてに記入があり、2件の判断が2/2件で一致し、根拠のない認証断定0件です。
表の設計整合性だけを検証し、認証情報の取得、接続、設定変更、実課金は行いません。
