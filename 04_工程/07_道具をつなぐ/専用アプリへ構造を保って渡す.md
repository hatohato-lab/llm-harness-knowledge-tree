## 1. 要点（一言と、根拠の段階と、使いどころ）

MCPは、AIと外部の道具をつなぐ通信規格です。
構造は、文字、図形、部品と、それらの関係を指します。
SQLは、データベースへの問合せや操作を書く言語です。

文章の案を、専用アプリで編集できる要素へ渡します。

根拠の段階：元の出典で確認

賢いモデルは、案から部品と関係を決める役に向きます。
軽いモデルには、要素と配置を具体的に渡します。
指示には、対象ファイル、形式、変更範囲を書きます。
図、画面、三次元の試作や、SQL案の受渡しに向きます。

根拠は仕組みや提供機能の確認です。
この環境での効果と動作は、まだ測っていません。

## 2. 仕組み（なぜ効くか）

画像や文章だけでは、後で部品を編集しにくい場合があります。
道具経由で専用アプリの要素を作ると、修正を続けられます。
FigmaとSplineの提供元で、構造を扱う操作を確認しました。
ほかの製品例は保存した資料に結び、互換性を一律にしません。

一枚の画像から形を作る例と、既存の場面編集は別です。
MeltFlex資料では、用途によって返る形式が異なります。
A5:SQL資料では、版によって使える操作が変わります。
形を作れた事実と、意図した形かどうかも分けます。

FigJamのローカル操作案も、同じ比較に含めます。
元実装と、無制限に使えるという主張は未確認です。
pen.devの投稿にある形式の詳細も、未確認です。

Claude Designには、既存の画面部品を送る同期手順があります。
色や余白だけでなく、実装済みの部品を設計案へ渡します。
これはMCP以外の受渡し例として扱います。
同期は外部への送信を伴います。今回は実行していません。

[Figmaの提供元](https://developers.figma.com/docs/figma-mcp-server/)は、フレームや部品などアプリ固有の要素を作成・変更できると説明しています。要素を分けて渡すと、文字だけ、位置だけといった修正対象を指定できます。[Illustrator用の公開実装](https://github.com/ymo6/illustrator-figure-mcp)も、構造検査と画像の見た目の検査を別に行います。したがって、編集可能性と見た目の両方を確かめる必要があります。

## 3. 使い方（手順と例）

以下は将来の試行手順です。今回は実行していません。

1. 成果物の形式と、後で編集したい要素を決めます。
2. 対象アプリとファイルや画面を特定します。
3. 現在ある部品や構造を読み取ります。
4. 一部だけを作り、表示と編集可能性を確かめます。
5. 保存場所、対象の識別子、残る差分を記録します。

指示や設計の例です。

```text
試験用の図を、文字と図形と矢印へ分けて設計します。
最初は、図形二つと矢印一本だけを対象にします。
保存先に加え、各要素を後から編集できるか確認します。
```

## 4. 試し方（最初の一歩と測り方）

最初の一歩は、準備10分、構造化20分、変更と検算15分の計45分です。
紙か手元のテキストで、図形2個、文字2個、矢印1本の架空図を作ります。
5要素に別々のIDを付け、文字列、位置、矢印の始点・終点を表へ書きます。
次に図形1個の位置だけを変更し、矢印が同じ対象を指すよう表を直します。

成功基準は、5/5要素を個別に指定でき、矢印の始点・終点が2/2正しく対応し、変更対象外の文字の変化が0件であることです。
変更時間と修正した項目数も記録します。
この初回は受渡しの構造設計を検証します。アプリへの送信はせず、FigmaやIllustratorでの実際の編集可能性・互換性は未検証です。

結果の件数を数え、上の成功条件と比べます。
