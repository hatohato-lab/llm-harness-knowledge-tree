## 1. 要点（一言と、根拠の段階と、使いどころ）

実装の前に、未決事項を解いて作業の共通仕様にします。

仕様は、作るものの動きと範囲を定めた記録です。
判断記録は、決めた案と理由を残す文書です。

根拠の段階：公式で確認

公式は、大きな機能の聞き取りと仕様化を案内します。
聞き取りによる時間短縮の量は未確認です。

使いどころは、複数工程へ渡す新機能や調査です。
賢いモデルには、曖昧な目的から論点を整理させます。
軽いモデルには、決定済みの具体的な仕様を渡します。
抽象的な目的と、具体的な合意を分けて書きます。

## 2. 仕組み（なぜ効くか）

資料で分かる事実と、本人が選ぶ判断を分けます。
判断を曖昧なまま分担すると、各担当が別々に補います。
先に同じ仕様を持てば、後続の解釈を比べられます。
これは工程上の推論です。

[公式の聞き取り例](<https://code.claude.com/docs/en/best-practices#let-claude-interview-you>)は仕様の文書化を勧めます。
[作者の質問手順](<https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/grilling/SKILL.md>)は質問の前提関係も扱います。
質問数を増やすだけでは、良い仕様にはなりません。

## 3. 使い方（手順と例）

1. 目的と、完成時の利用者の動きを書きます。
2. 読める資料から、既知の事実を確認します。
3. 結論を変える未決事項だけを質問します。
4. 決定、理由、対象外、用語を短く記録します。
5. 各作業へ、同じ仕様の版と該当箇所を渡します。

例は、研究資料を探せる小さな画面です。

| 項目 | 決定例 |
| --- | --- |
| 目的 | 保存済み資料を題名で探す |
| 決定 | 部分一致で探す |
| 理由 | 正式名を覚えていない場合に備える |
| 対象外 | Webからの自動収集 |
| 用語 | 資料は保存済みの1文書 |
| 未決 | 同名資料の並び順 |

すでに合意した条件は聞き直しません。
未決のまま進める場合は、仮定として区別します。
小さな明確な修正なら、短い仕様で足ります。

## 4. 試し方（最初の一歩と測り方）

最初は、上の題名検索の例を紙上で仕様にします。
準備5分、未決事項の決定と仕様化10分、読取り点検10分、修正と記録10分の計35分です。
外部サービスやAIの呼出しは不要です。

仕様を書く前に、次の架空の確認例を正解として固定します。

| 資料番号 | 題名 | 追加日 |
| --- | --- | --- |
| A | 工程の入門 | 2026-10-01 |
| B | 工程の入門 | 2026-10-02 |
| C | 文脈の整理 | 2026-10-03 |

入力は「工程」、期待結果は「B → A」の2件で、Cは含めません。
同名なら追加日が新しい順、という練習上の希望です。
実際の私の希望とは区別します。

1. 上の決定例と練習上の希望を使い、未決だった同名時の順序を決めます。
2. 目的、検索条件、同名時の順序、対象外、上記の確認例を各1行で書きます。
3. 仕様だけを別紙へ写し、最初の4項目を決定例と希望に、5番目を入力「工程」と期待結果「B → A」に照合し、一致数を数えます。

事前の合格条件は、5項目中5項目が一致し、決めたはずの事項が未決のまま残る数と、仕様にない条件を勝手に追加した数がともに0件です。
35分以内に1回まで直し、不一致数と必要な補足質問数を記録します。
これは仕様の抜けを探す独自練習です。別のモデルへ引き継げるか、実装後の訂正が減るかは未検証です。
実務へ移す際は、同じ仕様だけを渡した受け手の再質問数と、後の要件訂正数も記録します。
