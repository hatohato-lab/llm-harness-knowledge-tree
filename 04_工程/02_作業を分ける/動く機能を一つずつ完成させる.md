## 1. 要点（一言と、根拠の段階と、使いどころ）

一つの入力が結果へ届く小機能を、順に完成させます。

縦の分割は、入力から出力まで通る機能で分ける方法です。

根拠の段階：公式で確認

公式の長時間作業の報告で、段階実装を確認しました。
すべての仕事での改善率は未確認です。

使いどころは、新機能や文書処理の作成です。
賢いモデルには、利用者の目的から機能を切り出させます。
軽いモデルには、一機能と具体的な完成例を渡します。
分け方は抽象的に考え、着手条件は具体的にします。

## 2. 仕組み（なぜ効くか）

画面だけを作っても、利用者が目的を果たせるとは限りません。
小さくても入力と結果がつながれば、動きを確かめられます。
途中で止まっても、完成した部分を説明しやすくなります。

[Anthropicの実験報告](<https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents#incremental-progress>)は、一度に一機能を進めます。
多くを同時に作る失敗への対策として報告されています。
Webアプリ向けの報告であり、万能な証明ではありません。

## 3. 使い方（手順と例）

1. 利用者ができることを、動詞で列挙します。
2. 入力と結果がつながる最小の機能を選びます。
3. 必要な先行作業と、確認方法を添えます。
4. 一機能を作り、利用者の操作で確かめます。
5. 既存の動きを保ったまま、次の機能へ進みます。

資料検索なら、次の順が一例です。

| 作業 | 動くと分かること |
| --- | --- |
| 1件検索 | 題名を入力すると1件を開ける |
| 複数件表示 | 検索結果から資料を選べる |
| 絞り込み | 分類を選ぶと対象が減る |

これは独自の練習例です。
各部品を細切れにすること自体は目的ではありません。
全体を同時に変える移行には、別の分け方を使います。

## 4. 試し方（最初の一歩と測り方）

最初は手元のPowerShellで、題名3件から完全一致の1件を返す小機能を作ります。
固定配列を「工程の入門」「文脈の入門」「評価の入門」とし、入力した題名と一致する要素を返すだけにします。
準備5分、実装20分、動作確認15分、修正と記録10分の計50分を上限にします。
追加の導入や外部サービス、AIの呼出しは不要です。

作る前に、入力と期待結果を次の3件で決めます。

| 入力 | 期待結果 |
| --- | --- |
| 工程の入門 | 工程の入門を1件返す |
| 評価の入門 | 評価の入門を1件返す |
| 未登録 | 0件を返す |

事前の合格条件は、50分以内に3件中3件が一致し、完成した機能が1個、着手したままの別機能が0個です。
最初に3件が通るまでの分数と、修正回数も記録します。
この試行は入力から結果まで通す独自練習です。次の機能は今回は作りません。
時間内に通らなければ未完成と記録し、画面だけなどの部品を完成数に含めません。
実務では前の機能が壊れた回数と再修正時間も測ります。
