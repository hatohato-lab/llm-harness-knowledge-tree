## 1. 要点（一言と、根拠の段階と、使いどころ）

新旧の形を一時的に併存させ、利用側を順に移します。

互換性は、既存の利用側が引き続き動く性質です。
段階移行は、新形式の追加、利用側の移行、旧形式の整理です。

根拠の段階：元の出典で確認

作者の分割手順で、広い変更の例外を確認しました。
全体の移行時間が短くなるかは未確認です。

使いどころは、共通の名前や形式を広く変える仕事です。
賢いモデルには、利用側の広がりと順序を調べさせます。
軽いモデルには、一つの利用側の具体的な移行を渡します。
全体方針は抽象的でも、互換条件は具体的にします。
推論を多く使うモデルには、旧形式・新形式・利用側一覧・途中で保つ条件を渡します。
軽量モデルには、変更する利用側を1つに絞り、新旧それぞれの入力と期待結果を付けます。
この使い分けは試行案で、特定モデルでの効果を保証するものではありません。

## 2. 仕組み（なぜ効くか）

共通の形式を一度に置き換えると、多数の利用側が壊れます。
新形式を先に追加すれば、古い利用側を残したまま移せます。
最後の整理は、残った利用側がないことを条件にします。

[to-ticketsの広い変更の例外](<https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-tickets/SKILL.md>)に、この順序があります。
小機能への縦の分割が成り立たない場合の選択肢です。
新旧を併存させる分、一時的な管理負担は増えます。

## 3. 使い方（手順と例）

1. 変更する共通形式と、すべての利用側を調べます。
2. 古い形を保ち、新しい形を追加します。
3. 利用側を、小さなまとまりごとに移します。
4. 新旧の動きと、移行漏れを確かめます。
5. 全利用側の移行後に、旧形式の扱いを決めます。

独自例は、資料の識別子の名前変更です。

| 段階 | 例 |
| --- | --- |
| 追加 | 旧名と新名を読み取れるようにする |
| 移行 | 各読取処理を新名へ変える |
| 確認 | 旧名を使う箇所が残っていないか調べる |
| 整理 | 許可された範囲で旧名の扱いを決める |

削除などの操作は、その仕事での許可に従います。
各まとまりを単独で動かせない場合もあります。
その場合は、合流後に何を確かめるか先に決めます。

## 4. 試し方（最初の一歩と測り方）

最初は準備込み40分の紙上試行です。実物の変更や削除はしません。

1. 10分で、同じ値を持つ旧名 `id` と新名 `document_id`、旧名を読む利用側A・B・Cを用意します。
2. 20分で、①新名を併記、②Aを移す、③Bを移す、④Cを移す、⑤旧名を使わない状態、の5段階を表にします。
3. 10分で、各段階の利用側3つについて、読む名前が存在し同じ値を得るか確かめます。

事前の合格条件は、5段階×3利用側の15確認が15/15、途中で読めない利用側が0、最終段階の旧名参照が0です。
不合格なら、どの段階で何を先に変えたかを1件ずつ記録します。
この試行は移行順序の理解だけを測ります。実環境の互換性や所要時間は未検証です。
