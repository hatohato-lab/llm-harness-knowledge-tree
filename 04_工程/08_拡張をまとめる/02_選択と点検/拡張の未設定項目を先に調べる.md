## 1. 要点（一言と、根拠の段階と、使いどころ）

動かない拡張は、必要な設定がそろったか先に確認します。

userConfigは、作者が定義した利用者向けの設定項目です。

使いどころ：項目の照合は軽いモデルに向きます。
複数の原因を比べるときは、賢いモデルを使います。
部品の完全な名前と、未設定項目を具体に指示します。
接続先を持つ拡張の初期診断に向きます。

JSONは、項目名と値でデータを表す記述形式です。

根拠の段階：公式で確認

## 2. 仕組み（なぜ効くか）

設定不足と、接続先の故障は、見た目が似る場合があります。
先に必須項目を確認すれば、調べる順を決められます。

公式の `plugin configure` は、設定済み状態を示します。
引数には `name@marketplace` の完全な名前を渡します。
通常表示は保存値を出さず、設定の有無を示します。
JSON形式の出力は、非機密とされた保存値を含みます。
この機能は、Claude Code 2.1.285以降の説明です。

[公式のplugin configure仕様](https://code.claude.com/docs/en/plugins/cli-reference#plugin-configure)は、必須／任意と設定済み／未設定を別々に表示すると説明します。
まずこの2軸を数えると、値が足りない段階と、値がそろっても接続に失敗する段階を分けられます。
これは診断順序についての推論であり、接続先の正常性を保証する機能ではありません。

## 3. 使い方（手順と例）

1. 導入済み一覧から、完全な名前を確認します。
2. 作者が定義した設定項目を読みます。
3. 必須、任意、未設定の区別を一覧にします。
4. 不足分の準備方法を、作者の説明と照合します。
5. 将来設定した後は、読み直して状態を確認します。

確認用の例です。今回は実行していません。

```text
claude plugin list
claude plugin configure example@team-catalog
```

同梱の外部接続設定は、別の設定方式を使う場合があります。
秘密の値を、診断記録へそのまま貼りません。

## 4. 試し方（最初の一歩と測り方）

最初は、必要な設定の名前だけを一つの表にします。
必須の未設定数と、設定後の同一操作の成功率を測ります。
設定値がそろったことと、接続成功は別に記録します。

初回は準備込み30分の紙上試験です。実際の設定値や秘密情報は使いません。
5分で架空の4項目「api_url＝必須・設定済み、token＝必須・未設定、timeout＝任意・未設定、region＝必須・設定済み」を用意します。
15分で項目名、必須／任意、設定状態の表にし、最後の10分で答え合わせします。
成功条件は分類4/4件、必須の未設定1件、任意の未設定1件、設定済み2件を正しく数え、接続状態を「未確認」とすることです。
これで測るのは設定不足の見分け方です。接続試験の成功率は測れません。導入、設定変更、通信を伴わない試行案で、未実行です。
