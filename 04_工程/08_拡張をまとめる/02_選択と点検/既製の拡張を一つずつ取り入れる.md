## 1. 要点（一言と、根拠の段階と、使いどころ）

既製の一覧から、足りない部品を一つずつ試します。

カタログは、部品と配布元を探すための一覧です。

使いどころ：候補の比較は賢いモデルに向きます。
導入先と重複の照合は、軽いモデルでも行えます。
対象工程、追加する部品、除く部品を具体に指示します。
既存の環境を育てながら、便利な手順を学ぶ場面向けです。

プラグインは、追加部品をまとめた配布単位です。
ECCは、開発用の手順や設定を集めた外部の部品集です。

根拠の段階：元の出典で確認

## 2. 仕組み（なぜ効くか）

同時に多くの部品を変えると、効果の原因を追えません。
一つずつなら、増えた手間と減った手間を比べられます。
この理由は比較設計からの推論です。
導入による生産性の改善量は未測定です。

ECCの作者は、同じAIへの導入経路を一つに絞ります。
手動導入とプラグイン導入の重複を避けるためです。
Claude Code Templatesは、部品別の導入を用意します。
星数や収録数は、個々の品質の保証にはなりません。

[ECC作者の導入方針](https://github.com/affaan-m/ECC#pick-one-path-only-per-harness)は、同じ実行環境へ導入方法を重ねると技能・命令・フック等が重複しうると説明します。
[Claude Code Templatesの作者README](https://github.com/davila7/claude-code-templates#-quick-installation)には部品別の導入例があります。
この二つが、一つの部品と一つの導入経路に絞る判断の根拠です。改善の因果を比べやすいという部分は運用上の推論で、効果量は未測定です。

## 3. 使い方（手順と例）

1. 不足する工程を一つ決めます。
2. カタログから候補を三つまで選びます。
3. 元の手順と、追加される設定を読みます。
4. 既存の同名部品や同じ目的の部品を照合します。
5. 導入経路を一つにし、試験用の範囲で試します。
6. 続ける場合だけ、次の部品を選びます。

例：ECCの全工程ではなく、計画作成だけを比較します。
解除時にも、残る呼出し名や参照先の点検表を使います。
今回は導入、解除、削除を行っていません。

検索サービスのEmployeeStoreも、候補探しの一例です。
検索と出品申請は、別の操作として扱います。
Unityの公式拡張も、専門環境の準備とは分けて考えます。
手順を入れるだけで、エディターの準備は完了しません。

## 4. 試し方（最初の一歩と測り方）

最初は、既製の計画手順を一件読むだけで始めます。
既存手順との共通点と不足点を表にします。
将来の試用では、設定差分数と重複起動数を測ります。
同じ課題で、時間と手直し数も別に比べます。

解除後の残存数を述べる投稿もあります。
個別製品の残存数と、普遍的な不具合は未確認です。

初回は準備込み50分、紙上で計画手順1件だけを比較します。導入やモデル呼出しは不要です。
10分で練習課題「短い案内文を見直す」を選び、今の手順を3段階で書きます。
15分で[ECCの計画手順](https://raw.githubusercontent.com/affaan-m/ECC/main/commands/plan.md)を読み、要件の言い直し、危険箇所の確認、段階分けを既存手順と照合します。
15分で追加する点を最大1つ選び、残り10分で「既存にある／追加候補／今回不要」の3分類と、その理由を点検します。
成功条件は3観点すべての分類と理由がそろうこと（3/3）、既存と同じ役目を二重追加する案0件、次の試用対象0〜1件です。
追加不要でも成功です。この試験は差分と重複の見分け方を測り、導入の互換性や作業時間短縮は測りません。試行案であり未実行です。
