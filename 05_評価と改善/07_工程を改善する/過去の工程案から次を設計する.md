## 1. 要点（一言と、根拠の段階と、使いどころ）

過去の工程と成績を材料に、次の工程案を設計する型です。

根拠の段階：**論文で確認**。

工程案の保管庫は、手順と成績を対で残す場所です。
Meta Agent Searchは、その保管庫を使う探索法です。
過去の設計と成績を、次の設計役へ文脈として渡します。
親の候補を選んで一点ずつ変える木探索とは分けます。
ADASは、AIの働く仕組みを自動設計する研究領域です。

設計には過去案と失敗の関係を読める推論用モデルが向きます。
実行は短い指示に従う軽量な対話モデルでも、成績を確かめて選べます。
指示では設計目的を抽象的に、変更範囲と採点を具体的に書きます。
同種の調査、読解、コード修正を繰り返す場面に向きます。
この使い分けは実務への提案です。

## 2. 仕組み（なぜ効くか）

論文では、設計役が工程をコードとして作ります。
課題で測った成績と一緒に保管し、次の設計に渡します。
その場で最高点でない案も、後の組み合わせに使えます。
第3節と第4節は、この探索と実験を示しています。
[原論文](https://arxiv.org/html/2408.08435v2)

仕組みの要点は、成功案だけを唯一の正解にしないことです。
違う発想を残すと、行き詰まり時に戻る足場ができます。
ただし、保存するだけで改善するという証明はありません。
私の文書作業での効果は未確認です。

## 3. 使い方（手順と例）

以下は、研究を小さく試すための簡略案です。

1. 現行工程、採点方法、試行の上限を決めます。
2. 過去の案、成績、失敗理由を一つの表に並べます。
3. 設計役に、新しい案を一つ提案させます。
4. 同じ課題と実行条件で、現行案と比べます。
5. 不採用案も理由付きで保管します。
6. 未使用の課題で確かめ、採用する版を決めます。

たとえば、資料要約の工程を改善します。
案Aは「読んで要約」、案Bは「主張を抜いて要約」です。
案Cでは、両案の失敗から「根拠の照合」を組み込みます。

```text
目的：根拠のない断定を減らす。
変更範囲：資料を読む順序と確認工程。
固定条件：資料、実行モデル、採点基準。
入力：過去の工程案、成績、失敗例。
出力：新案、過去案との差、期待する改善。
```

## 4. 試し方（最初の一歩と測り方）

以下の55分・件数・判定値は、学習用の提案です。
論文の実測値や、効果を証明できる標本数ではありません。
導入済みのモデルと短い資料を使い、現行案と新案一つを比べます。

1. 10分で、練習用3件と未使用の確認用2件を分けます。
   各資料には正しい事実を二つ選び、要約に両方を残す採点表を作ります。
2. 10分で、現行工程・過去の失敗・成績を表にし、新案一つを設計します。
3. 25分で、両案を練習3件と確認2件に1回ずつ適用します（計10出力）。
   資料、実行モデルの版、生成設定、採点基準は同一にします。
   新案は確認2件を見る前に確定し、その結果で書き直しません。
4. 10分で、正しい二つの事実を保ち、根拠のない追加がない件数÷5を比べます。
   練習3件の合格が現行より1件以上増え、確認2件は両方合格し、
   全5件の根拠のない断定が0件なら、次の検証に進む候補として残します。

設計時間と実行時間を分け、実行時間が現行の1.5倍を超える案は保留にします。
55分で打ち切り、未完了は成功に数えません。
追加工程の呼出し回数も残し、採用後の費用を考える材料にします。

採点方法を工程案と同時に変えると、比較が崩れます。
採点側を固定し、変更対象から外します。
生成コードを実行する原方式の再現は、ここでは行いません。
文書で模す方式と原方式の同等性は未確認です。
