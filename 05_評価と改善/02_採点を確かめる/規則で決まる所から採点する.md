## 1. 要点（一言と、根拠の段階と、使いどころ）

**一言：数値や形式は、同じ条件で動く規則に任せる。**

根拠の段階：公式で確認。

モデル：軽量な汎用モデルにも推論型モデルにも使う。規則採点自体には言語モデルを使わない。
指示：文字列、数値、許容幅を具体的に指定する。
作業：分類、計算、必須項目、ファイル形式の確認に向く。

## 2. 仕組み（なぜ効くか）

規則採点は、条件式で合否を決める方法である。
同じ入力と規則なら、同じ結果を得やすい。
公式文書は、完全一致などの規則採点を紹介する。[1]
一方、意味が同じ別表現まで落とす弱点がある。

以下は、その性質を使う実務案である。
先に確定できる項目を分けると、見直す量を減らせる。
文章の意味や根拠の妥当性は、別の採点に残す。

## 3. 使い方（手順と例）

1. 合否を機械で決められる項目を列挙する。
2. 空白や大文字など、無視してよい差を決める。
3. 数値なら単位と丸め方も固定する。
4. 正しい例と誤った例で、規則自体を試す。
5. 規則の結果と、意味の採点を別欄に残す。

例：分類結果は「肯定・否定・混合」の一致で測る。
説明文の説得力は、分類の一致率へ混ぜない。
金額なら「100円」と「100ドル」を同一視しない。
これは例示であり、特定作業の正解規則ではない。

JSONは、項目名と値を組にしたデータ形式である。
JSON Schemaは、その項目と値の型を決める規則である。
構造化出力は、決めた項目構成で返す出力である。
形式への適合と、回答内容の正しさは分けて測る。
Claude Code公式にも、構造化出力の指定がある。[2]
formatは、JSON Schemaで値の形式を示す属性である。
例えば、emailはメールアドレス形式を表す。
Claude Codeは、この属性を注記として扱う。
その形式条件は強制されず、別の検査が必要である。[2]
失敗や上限到達も、形式が読めるだけで成功扱いしない。

ECCは、Claude Code向けの公開拡張集である。
その監査定義は、固定スクリプトの採点結果を使う。[3]
適用項目で満点が変わるため、点数と満点を共に残す。
この構成点は、生成コードの正しさを保証しない。

## 4. 試し方（最初の一歩と測り方）

最初は45分で、必須見出しの検査規則だけを試す。
以下の件数・時間・合格線は、学習用の提案であり、実測値ではない。

1. 10分で短い回答10件を選び、人が合格5件・不合格5件に分ける。
   合格側には許される表記ゆれ、不合格側には見出し欠落を含める。
2. 15分で、必須見出しの一致と、無視してよい空白の規則を書く。
3. 10分で、固定した10件を同じ規則で2回検査し、各件の結果と確認秒数を残す。
4. 10分で、人の固定した正解表と照合する。正答の誤落ち/5、誤答の見逃し/5、
   2回の一致件数/10、手作業と規則の1件当たり確認秒数を記録する。

誤落ち0/5、見逃し0/5、再実行の一致10/10なら、この見出し規則を採用候補にする。
時短も目的なら、規則の確認秒数/手作業の確認秒数が1未満かを別に判定する。
作成時間は確認時間に混ぜず、初期費用として残す。失敗した例は規則を直した後、
同じ10件で再検査する。これだけで未知の回答への正確さを保証したとはしない。

規則を通ることと、成果全体が正しいことは別である。
引用先の存在だけでは、主張の裏付けを証明できない。
