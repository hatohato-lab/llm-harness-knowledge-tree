## 1. 要点（一言と、根拠の段階と、使いどころ）

同じ失敗を起こす条件を残し、原因候補を一つずつ確かめます。

再現は、同じ条件で失敗をもう一度起こすことです。
ログは、実行中の出来事を残した記録です。
仮説は、観測で確かめる原因の候補です。

**根拠の段階：公式で確認**

賢いモデルは、複数の原因候補と予測を組み立てます。
軽いモデルは、時刻やエラー箇所の整理から試します。
指示は具体的にし、期待結果、実際の結果、再現条件を渡します。
不具合、遅さ、道具の失敗、設定変更後の異常に向きます。
モデルの使い分けは、本葉の試行案です。

## 2. 仕組み（なぜ効くか）

公式は、再現手順とエラー情報を渡す方法を勧めます。
一定して起きる失敗か、時々起きる失敗かも区別します。
最小の再現例は、疑うべき条件を減らします。

作者の診断手順は、複数の仮説と予測を先に立てます。
一条件ずつ変えることで、予測と観測を照合できます。
症状が消えた事実と、根本原因が分かった判断を分けます。
仮説比較がいつも最短で解決するという保証はありません。

再現情報の渡し方は[公式の不具合修正](https://code.claude.com/docs/en/common-workflows#fix-bugs-efficiently)、条件を減らす理由と一変数ずつの観測は[作者の診断手順](https://github.com/mattpocock/skills/blob/main/skills/engineering/diagnosing-bugs/SKILL.md)に基づきます。
作者の手順は、先に症状を検出できる試験を作り、それから最小化、仮説、観測へ進みます。検査が失敗を拾わないまま原因だけを考え始めないためです。

## 3. 使い方（手順と例）

1. 期待結果、実際の結果、環境、時刻をそろえます。
2. 同じ失敗が起きる最小の入力と操作を探します。
3. 原因候補を挙げ、候補が正しい場合の予測を書きます。
4. 予測を区別できるログや小さな実験を選びます。
5. 一度に変える条件を一つにして、採否の証拠を残します。
6. 修正の前後で、元の再現手順と必要な検査を比べます。

例は、仕組みを理解するための試行用です。

```text
期待結果と実際の結果を、最初に分けてください。
原因候補ごとに、正しければ観測できる事実を書いてください。
今あるログで確かめられる候補から調べます。
却下した候補と、その証拠も残してください。
再現できない場合は、解決済みとせず未確認としてください。
```

設定の影響は、設定を消さず一時的に外して比較できます。
Claude Codeには、追加設定を外す診断用の起動方法があります。
ただし、認証や権限、管理設定などは残ります。
症状が残っても、設定全体が無関係とはいえません。
診断用の比較後は、通常の条件で再び確かめます。

外部の実行記録でも、失敗行と変更時刻を対応付けます。
接続失敗では、一時切断、認証不足、版の不一致を分けます。
周辺サービスに原因がある場合も、同じ時刻の証拠を集めます。
専用のサービスへ接続する操作は、この型の必須条件ではありません。

## 4. 試し方（最初の一歩と測り方）

過去の小さな不具合を一つ選び、修正前の失敗を記録します。
原因候補を二つ書き、区別できる観測を一つ探します。

再現率、調査時間、試した仮説数、同じ仮説の再試行数を残します。
時々起きる失敗では、一回の成功だけで解消と判断しません。

ログにない情報を、AIの説明だけで事実にしません。
原因候補をまとめて変えると、どれが効いたか分からなくなります。
診断用の起動は、安全性を強める仕組みではありません。

**40分で行う練習案（件数と基準は本葉の提案）**

1. 5分で仕様を「2以上なら合格」と書き、入力1、2、3の正解を「不合格、合格、合格」に固定します。練習用の誤った判定式は「入力が2より大きい」です。紙上の計算で構いません。
2. 10分で3入力を同じ式で2巡し、各入力の値と判定をログ表に残します。境界の2で失敗することを確認し、原因候補を「値の読み違い」「比較に等号がない」の2つにします。
3. 10分で候補ごとの予測を書きます。ログに入力2が正しく残っていれば読み違い説は弱まり、式だけを「2以上」に変えて境界が通れば比較条件説を支持します。一度に変える条件は式の等号だけです。
4. 10分で同じ入力1、2、3を同じ順序で2巡し、修正前後の正解数/6、境界入力の失敗数/2を比べます。5分で原因と却下理由を各1行残します。

練習の合格は修正後6/6正解、境界の失敗0/2、候補2件とも採否の証拠あり、40分以内です。
修正前は正解4/6となるよう設計した教材で、実際の不具合改善率ではありません。
現実の断続的な障害へ適用するときは、この少数試行だけで解消を保証しません。
